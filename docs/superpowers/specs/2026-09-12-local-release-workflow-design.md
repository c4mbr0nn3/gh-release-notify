# Spec: Local-driven release workflow

Replaces the cargo-release-in-CI design documented in
`docs/superpowers/specs/2026-07-05-release-workflow-design.md` (superseded).

## Objective

The current release pipeline (single `workflow_dispatch` workflow that runs
cargo-release inside CI) is broken: floating toolchain × floating `^1`
cargo-release range caused repeated CI failures (MSRV drift), the verification
gate runs against the pre-bump commit, and a post-tag build failure leaves a
half-published release with no recovery path.

New model: **the release starts locally**. A script infers the bump from
conventional commits, generates the changelog, runs the verification gate,
commits, tags, and pushes. CI reacts to the new tag: it re-runs the gate,
scans what we own, builds and pushes the multi-arch Docker image, and creates
the GitHub Release. Irreversible steps are pushed to the point where they are
least likely to fail, and every failure mode has a documented recovery.

## Resolved decisions (from grilling session 2026-09-12)

| Decision | Choice |
|---|---|
| Tooling | Thin bash script wrapping git-cliff + cargo-release (option A) |
| Bump inference | git-cliff defaults: breaking→major, feat→minor, fix and everything else→patch; nothing skipped |
| Changelog | `CHANGELOG.md` at root, Keep-a-Changelog, generated by git-cliff, committed in the release commit |
| Local gate | Hard gate (fmt/clippy/test) before any commit; dry-run skips it |
| Modes | `--dry-run` only (no intermediate modes) |
| Safety rails | Refuse on: dirty worktree, off-main, unpushed commits, existing `v{next}` tag, zero commits since last tag |
| Toolchain pin | Exact `1.98.1` in CI and Dockerfile builder; bumped together in one commit, always |
| Vuln scanning | Trivy `fs` early gate + Trivy `image --ignore-unfixed` late gate; SARIF to Security tab |
| Release body | git-cliff-rendered changelog section for the tag |
| Post-tag CI failure | Fix forward on a new patch (documented) |
| OCI | SBOM + provenance attestations; no signing |
| `latest` tag | Automatic on every release |
| Old workflow | Deleted outright; old spec/plan marked superseded |

## Tech stack

- `git-cliff` 2.14.1 (pinned; MSRV 1.88) — bump inference + changelog
- `cargo-release` 1.1.5 (pinned; MSRV 1.92) — version bump, release commit, tag
- Rust toolchain 1.98.1 (exact pin, matches Dockerfile builder)
- GitHub Actions, docker buildx, Trivy

## Commands

```bash
# Release (infer bump from commits since last tag):
./scripts/release.sh

# Release with explicit level (overrides inference):
./scripts/release.sh --major | --minor | --patch

# Preview only: prospective version, changelog section, planned actions.
# Writes nothing, commits nothing, pushes nothing, skips the local gate:
./scripts/release.sh --dry-run
./scripts/release.sh --dry-run --minor

# Tool install (script requires presence, refuses to install anything):
cargo install git-cliff --locked --version 2.14.1
cargo install cargo-release --locked --version 1.1.5

# CI is automatic: on push of tag v*
```

## Script behavior (scripts/release.sh)

1. **Dependency check**: `git-cliff` == 2.14.1, `cargo-release` == 1.1.5.
   On missing/mismatch, print the exact pinned install command and abort.
   The script installs nothing; its perimeter is the release, nothing else.
2. **Safety rails** (non-overridable, in order):
   - worktree clean (`git diff --quiet` against HEAD and remote)
   - HEAD on `main`
   - `main` fully pushed (`git status` shows no unpushed commits)
   - next version tag `v{next}` does not exist locally or on any remote
   - at least one commit since last tag (else: "nothing to release", refuse)
3. **Bump determination**:
   - default: `git cliff --bumped-version` (inference)
   - `--major|--minor|--patch`: `git cliff --bumped-version --bump <level>`
4. **Dry-run** (`--dry-run`): print prospective version, inferred (or forced)
   level, the changelog section (`git cliff --unreleased --bump [--bump <level>]`),
   and the planned commit/tag/push actions. Exit 0. Write nothing.
5. **Local gate** (skipped only in dry-run): `cargo fmt --check`,
   `cargo clippy -- -D warnings`, `cargo test`. Any failure aborts before any
   state is written.
6. **Execute**: `cargo release --config release.toml --execute --no-confirm`
   (with `--bump <level>` when a level flag was given). cargo-release:
   - bumps `Cargo.toml` + `Cargo.lock`
   - runs `pre-release-hook = ["git", "cliff", "--unreleased", "--tag",
     "v{{version}}", "--prepend", "CHANGELOG.md"]` so the changelog lands in
     the same release commit
   - commits `chore: release v{version}` (subject-only, Conventional Commits)
   - tags `v{version}`, pushes branch + tag
7. On any failure after the push: **fix forward on a new patch**. Documented
   in the script header and AGENTS.md. No tag deletion, no revert dance.

## CI workflow (release.yml, tag-triggered)

`on: push: tags: ['v*']` — no `workflow_dispatch`, no inputs.

Permissions: job-scoped `contents: write` (release creation) +
`packages: write` (GHCR push). No workflow-level write grants.

Job steps, in order:

1. Checkout; Rust toolchain pinned exact `1.98.1` (rustfmt + clippy).
2. **Gate**: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`.
   (The tagged commit is what ships; local gate + this gate close the
   pre-bump-verification gap of the old design.)
3. **Early vuln gate**: `trivy fs --severity HIGH,CRITICAL --exit-code 1 .` —
   Cargo.lock dependency advisories + Dockerfile misconfig checks. Pre-build,
   fast-fail, blocking. Everything here is ours to fix.
4. Buildx multi-arch (`linux/amd64,linux/arm64`) with `provenance: true`,
   `sbom: true`, OCI 1.1 annotations via docker/metadata-action. Tags:
   `v{version}`, `{version}`, `latest`. Push to `ghcr.io/c4mbr0nn3/gh-release-notify`.
5. **Late vuln gate**: `trivy image --ignore-unfixed --severity HIGH,CRITICAL
   --exit-code 1` on the pushed image. Blocks only on findings with an
   available fix — i.e., remediable by rebuilding. Unfixable Debian backlog
   never blocks.
6. Both scans upload SARIF to the GitHub Security tab (visibility for
   everything that does not block).
7. Install `git-cliff --locked --version 2.14.1` (MSRV 1.88 < 1.98.1 pin).
8. Render release body: `git cliff --unreleased --tag v{version}` against the
   repo's `cliff.toml`.
9. Create GitHub Release on the tag with the git-cliff body.

Failure semantics: the tag is already on `main` when CI runs; a failed CI means
no image and/or no GitHub Release for that tag. Recovery is fix-forward on a
new patch. This is accepted and documented.

## Dockerfile

- Builder: `rust:1.98.1-slim` — **exact pin**, bumped only via commit, always
  in lockstep with the CI toolchain pin.
- Runtime: `debian:bookworm-slim` — **floating** on purpose, to absorb Debian
  security patches; Trivy `--ignore-unfixed` is the gate that catches what
  floats in. (We do not block on Debian CVEs we cannot act on — a rebuild is
  the remediation, and blocking criteria are limited to fixable findings.)
- Otherwise unchanged: multi-stage, non-root user, dep-layer caching.

## Code style

- `scripts/release.sh`: bash, `set -euo pipefail`, comments allowed (script is
  documentation), plain functions (`check_deps`, `check_state`, `dry_run`,
  `execute_release`), no global mutable soup.
- `cliff.toml` / `release.toml` / `Dockerfile` / workflows: comments allowed
  (documentation files per AGENTS.md rules).
- Commit messages: Conventional Commits, subject-only, <= 72 chars,
  imperative mood. Release commit: `chore: release v{version}`.

## Testing strategy

- The release script is glue over well-tested tools; it is exercised manually:
  `--dry-run` (inference + explicit level + refuse states) and a real patch
  release as the final smoke test.
- CI workflow is verified by the real release it produces.
- `cargo fmt` / `cargo clippy -- -D warnings` / `cargo test` remain the
  project gate; no new unit tests are added by this change (no Rust source
  is touched except none at all).
- Actionlint (if available) lints the workflow YAML; otherwise YAML schema
  sanity is on the release smoke test.

## Boundaries

- **Always**: keep Dockerfile and CI toolchain pins in lockstep (one commit);
  run the full verification gate before claiming done; conventional commits.
- **Ask first**: changing pinned tool versions; changing the Trivy blocking
  criteria; adding new release tooling.
- **Never**: re-introduce floating version ranges for release tooling
  (`^1` etc.); install tools from within the release script; make the script
  do anything beyond the release; HTML email / other AGENTS.md out-of-scope
  items (unchanged).

## Success criteria

- `./scripts/release.sh --dry-run` prints version, level, changelog section,
  and planned actions; writes nothing to disk or git.
- `./scripts/release.sh` with any unsatisfied safety rail refuses with a
  specific message and exits non-zero before writing anything.
- A real `patch` release: local gate runs, release commit contains Cargo.toml
  + Cargo.lock + CHANGELOG.md, tag `v{X.Y.Z+1}` pushed, CI triggers on the
  tag, gate passes, both Trivy gates pass, image with `{tag}`, `{version}`,
  `latest` + SBOM + provenance lands on GHCR, GitHub Release created with
  the git-cliff changelog body.
- Old `release.yml` (workflow_dispatch + cargo-release in CI) is gone;
  `release.toml` contains no CI-era leftovers.
- AGENTS.md Releases section describes the new flow; old spec/plan carry a
  superseded header pointing here.
